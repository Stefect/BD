# 2. Архітектурне рішення: логіка залишків і статусів накладних на рівні БД

## Статус
Прийнято. Доповнює ADR 0001 (пункт 2 про складені ключі і пункт 3 про inventory_stock).

## Контекст
ADR 0001 описує `inventory_stock` як операційний стан залишків, але не визначає, хто його змінює. Перший аудит показав: накладна може стати `received` без збільшення залишків, переміщення можуть зробити залишок від'ємним, сума накладної не контролюється. Це розбіжність між описом бізнес-логіки і обмеженнями БД.

Розглянуто два варіанти:
1. **Логіка в застосунку.** Простіше, але будь-який клієнт (pgAdmin, скрипт, інший сервіс) може обійти правила.
2. **Логіка в БД (тригери і функції).** Правила діють незалежно від клієнта.

## Рішення
1. Залишки (`inventory_stock`) змінюють лише тригери:
   - `trg_order_receive`: при переході накладної `draft` в `received` збільшує залишки в `location_id` кожної позиції.
   - `trg_movement_apply`: при вставці переміщення зменшує залишок у відправника і збільшує у отримувача (для списання лише зменшує).
   - Функція `fn_adjust_stock` відхиляє від'ємний залишок і переповнення комірки (`max_capacity`).
2. Статусна модель накладної контролюється тригерами: `draft` в `received` або `cancelled`, інші переходи відхиляються. Отримання без позицій відхиляється.
3. Позиції накладної змінюються лише в статусі `draft` (`trg_item_guard`).
4. Сума накладної (`total_cost`) перераховується тригером `trg_item_total` після кожної зміни позицій.
5. Журнал переміщень незмінний (`trg_movement_immutable`). Для аудиту додано `created_by`, `movement_date`, `reason`.
6. Для звітів додано представлення `v_stock_by_product`, `v_low_stock`, `v_location_load`.
7. Партія (`batch_number`) і термін придатності (`expiry_date`) зберігаються в позиції накладної. Залишки ведуться без розбивки за партією (обмеження, див. `spec.md`, розділ 7).
8. Email унікальний без урахування регістру (індекс на `lower(email)`). Дати зберігаються як `TIMESTAMPTZ`. Для FK додано індекси.

## Наслідки
- Позитивні: цілісність не залежить від клієнта; будь-яке порушення правила дає зрозуміле повідомлення від БД; історія переміщень незмінна; сума і залишки не розходяться.
- Негативні: логіка частково в SQL, її треба підтримувати разом зі схемою; тригери ускладнюють масові вставки (кожен рядок обробляється окремо). Для лабораторної обсяг даних малий, тому це несуттєво.
- Прямий `UPDATE inventory_stock` адміністратором можливий, оскільки права на таблицю не обмежено. Для продуктивної системи варто відкликати право запису у ролі застосунку.
- Тести правил: `docs/adr/tests.sql`. Кожне правило має окремий тест (T01..T19).
